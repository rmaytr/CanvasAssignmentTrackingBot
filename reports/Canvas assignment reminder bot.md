# Poll the Planner, Nudge Through Telegram

A student can build this bot alone, for $0 a month, as a single-user, self-hosted Python service that polls Canvas's **`GET /api/v1/planner/items`** endpoint with their own personal access token, sends a ranked 8 AM digest and one consolidated "due in under 24 hours" reminder every two hours through a **Telegram bot with Done and Snooze buttons**, and runs one idempotent tick loop backed by SQLite on an always-on machine such as a Raspberry Pi, a free Oracle or Google VM, or a roughly €5-a-month VPS. The planner endpoint is the same call the Canvas To Do sidebar makes, and it already returns each student's own due dates and submission flags, so "stop when submitted" is a polling problem rather than a scraping problem. The gap is real: Canvas has no automatic pre-deadline reminder (a 2018 feature request for one is still open), and none of the roughly 17 open-source Canvas tools surveyed pairs a prioritized digest with reminders that repeat until the work is submitted. The hardest constraint is access, not engineering, because Canvas core now forces student tokens to expire within 120 days and a growing list of universities stops students from creating tokens at all, so the PRD needs a fallback mode built on the calendar feed with a manual "Done" button. Self-hosting is also the only shape that fits Instructure's policy, which forbids apps that ask other users to paste in their tokens, so the public repository should distribute software and never run a hosted service. Two choices should be ruled out from the start: SMS, because US carriers have required paid 10DLC registration since February 2025 and the free email-to-text gateways have shut down, and GitHub Actions cron as the scheduler, because GitHub documents that scheduled runs can be delayed or dropped and one user reported runs 8–14 hours late.

## Canvas's To Do sidebar is an API call the bot can make too

The student's Canvas To Do list is not a page to scrape; it is a JSON request. The planner front-end fills the sidebar with **`GET /api/v1/planner/items` using `filter=incomplete_items`, `order=asc`, a start date two weeks back and 14 items per page** ([canvas-lms sidebar-actions.js](https://raw.githubusercontent.com/instructure/canvas-lms/master/ui/shared/planner/actions/sidebar-actions.js)), and the server code confirms that for students the dashboard is "just using planner now" ([canvas-lms users_controller.rb](https://raw.githubusercontent.com/instructure/canvas-lms/master/app/controllers/users_controller.rb)). The endpoint merges assignments, ungraded quizzes, ungraded discussions and pages that have to-do dates, calendar events, peer reviews, discussion checkpoints and the student's own planner notes into one sorted stream, covering two weeks back to two weeks ahead and 50 items per page by default ([planner_controller.rb](https://raw.githubusercontent.com/instructure/canvas-lms/master/app/controllers/planner_controller.rb)). Each item carries a `plannable_date` that is already the **student-specific due date after section and individual overrides**, a `planner_override` holding the "mark as done" flag, and a `submissions` hash with `submitted`, `excused`, `graded`, `late`, `missing`, `needs_grading` and `redo_request` ([lib/api/v1/planner_item.rb](https://raw.githubusercontent.com/instructure/canvas-lms/master/lib/api/v1/planner_item.rb)). One call therefore answers all three of the bot's questions — what is due, when, and is it already done — across every course.

The bot should decide "done" the way Canvas does, then tighten the rule in two places. Canvas counts an item as complete when the student marked it complete, or when a submission exists, no redo was requested and the student has not explicitly marked it incomplete ([lib/plannable.rb](https://raw.githubusercontent.com/instructure/canvas-lms/master/lib/plannable.rb)). The bot should additionally **stop reminders for excused work**, which Planner still counts as incomplete, and should treat a teacher-entered grade with no submission as done only for the offline types `on_paper`, `none` and `external_tool`, which Canvas groups as `OFFLINE_SUBMISSION_TYPES` because they never produce an online submission ([abstract_assignment.rb](https://raw.githubusercontent.com/instructure/canvas-lms/master/app/models/abstract_assignment.rb)). For online work, a teacher-entered zero on a missing assignment should stay visible in an overdue section rather than vanish; the most-starred Canvas-to-Todoist script made exactly that mistake, ignoring graded items so that a "0" hid work the student could still submit ([scottquach README](https://github.com/scottquach/Canvas-Assignments-Transfer-For-Todoist)). One field to avoid entirely is `has_submitted_submissions`, which is true if *any* student in the course submitted and so says nothing about this student ([assignments_api_controller.rb](https://raw.githubusercontent.com/instructure/canvas-lms/master/app/controllers/assignments_api_controller.rb)).

The other endpoints a student can call are narrower views that drop items by design. **`/api/v1/users/self/todo`** only looks at work due from four weeks back to one week ahead, caps results at 15 by default, caches for 15 minutes, hides anything the student clicked "ignore" and leaves out peer reviews ([user_learning_object_scopes.rb](https://raw.githubusercontent.com/instructure/canvas-lms/master/app/models/user_learning_object_scopes.rb); [users_controller.rb](https://raw.githubusercontent.com/instructure/canvas-lms/master/app/controllers/users_controller.rb)), while **`/users/self/upcoming_events`** stops at 20 items and seven days despite being documented as paginated ([canvas-lms user.rb](https://raw.githubusercontent.com/instructure/canvas-lms/master/app/models/user.rb)). Two supporting calls remain worth making. `missing_submissions?filter[]=submittable` feeds a past-due section, and `/courses/:id/assignments?include[]=submission` supplies what Planner omits — `points_possible`, `submission_types` and `assignment_group_id` — and is the only route to **undated assignments, which never appear in Planner, the To Do list or the calendar feed** (`bucket=undated`) ([sorts_assignments.rb](https://raw.githubusercontent.com/instructure/canvas-lms/master/lib/sorts_assignments.rb)). The assignment-group weights that prioritization needs come back in one GraphQL round trip through `AssignmentGroup.groupWeight`, using the same token at `POST /api/graphql` with permissions that mirror REST ([graphql.md](https://raw.githubusercontent.com/instructure/canvas-lms/master/doc/api/graphql.md); [assignment_group_type.rb](https://raw.githubusercontent.com/instructure/canvas-lms/master/app/graphql/types/assignment_group_type.rb)). GraphQL has no planner equivalent, so it complements the REST call rather than replacing it. The Python `canvasapi` library (v3.6.0, April 2026) wraps To Do, planner notes, overrides and GraphQL but has **no method for `/planner/items`** ([PyPI canvasapi](https://pypi.org/pypi/canvasapi/json); [canvasapi canvas.py](https://raw.githubusercontent.com/ucfopen/canvasapi/develop/canvasapi/canvas.py)), which argues for a small custom client over the handful of endpoints the bot needs.

Polling is cheap enough to catch a submission within minutes. Canvas throttles each token with a leaky-bucket quota and says "any API client that makes no more than one simultaneous request is unlikely to be throttled"; every response carries `X-Request-Cost`, and hosted Canvas returns 429 when it throttles ([throttling.md](https://raw.githubusercontent.com/instructure/canvas-lms/master/doc/api/throttling.md)), although the open-source middleware still defaults to 403 with "Rate Limit Exceeded" in the body, so the client should treat both codes as throttling ([request_throttle.rb](https://raw.githubusercontent.com/instructure/canvas-lms/master/app/middleware/request_throttle.rb)). The planner response is cached on the server, but the cache key includes the user's and the courses' last-updated times, saving a submission touches the user record, and the controller honors ETags, so a conditional `If-None-Match` poll returns 304 until something actually changes ([planner_controller.rb](https://raw.githubusercontent.com/instructure/canvas-lms/master/app/controllers/planner_controller.rb); [submission.rb](https://raw.githubusercontent.com/instructure/canvas-lms/master/app/models/submission.rb)). A sequential sync every 10–15 minutes while the student is awake, every 30–60 minutes overnight, and once more immediately before each digest and each reminder limits the "reminded after already submitting" window to a single poll interval. Three protocol details are mandatory: follow the opaque `Link` headers for pagination ([pagination.md](https://raw.githubusercontent.com/instructure/canvas-lms/master/doc/api/pagination.md)); parse timestamps as ISO 8601 UTC while still accepting the offset form that appears in some doc examples ([doc/api/README.md](https://raw.githubusercontent.com/instructure/canvas-lms/master/doc/api/README.md)); and send a descriptive User-Agent, because **Instructure began enforcing User-Agent headers in production on June 20, 2026** and scripts without one now receive 403 ([Instructure Community](https://community.instructure.com/en/discussion/658205/enforcing-user-agent-header-for-canvas-api-requests/p1); [University of Melbourne](https://lms.unimelb.edu.au/updates/features-and-improvements/feature-update-enforcing-user-agent-header-for-canvas-api-requests)).

Several item types never produce a submission and need a manual "Done": paper, external-tool and no-submission assignments, ungraded pages and discussions with to-do dates, and planner notes. Peer reviews arrive as `assessment_request` or `peer_review_sub_assignment` items dated by the peer-review deadline, and checkpointed discussions arrive as `sub_assignment` items with a required reply count ([planner_item.rb](https://raw.githubusercontent.com/instructure/canvas-lms/master/lib/api/v1/planner_item.rb)). `lock_at`, the "available until" date, is a second and harder deadline worth surfacing for late work that can still be submitted. One behavior could not be confirmed from source — when a New Quiz (an external LTI tool) sets `submitted_at` on the Canvas submission — so the PRD should budget a short test against a real quiz.

### Personal tokens work for self-use but now expire within 120 days

A student creates a personal access token under Account › Settings › "+ New Access Token". Canvas core now requires a stated `purpose` on every token and, for users enrolled only as students, an expiry **no more than 120 days out** ([tokens_controller.rb](https://raw.githubusercontent.com/instructure/canvas-lms/master/app/controllers/tokens_controller.rb)); some schools go shorter, and Stanford previously required student tokens to expire after 30 days ([Stanford gocanvas](https://gocanvas.stanford.edu/news/canvas-update-summer-2026)). Unless the school has enabled scopes on its default developer key, the token "will inherit the user's permissions" — full student access, not read-only access ([tokens_controller.rb](https://raw.githubusercontent.com/instructure/canvas-lms/master/app/controllers/tokens_controller.rb)). Admins also have a switch that blocks student token creation, and schools use it: **UW–Madison** stopped student self-service tokens on November 14, 2025 ([UW–Madison KB](https://kb.wisc.edu/luwmad/156712)); **Ohio State** restored instructor tokens in August 2026 while "students will still not be able to generate personal access tokens" ([OSU IT](https://it.osu.edu/news/2026/08/11/carmencanvas-personal-access-tokens)); **Texas A&M** and **St. Edward's** do not give tokens to students ([TAMU](https://lms.tamu.edu/support-resources/canvas-api-access-token-request.html); [St. Edward's](https://support.stedwards.edu/TDClient/96/Portal/KB/Article/6479/Canvas-API-Access-Tokens)); and the **University of Missouri System** does not approve them, noting that tokens "circumvent multi-factor authentication" ([UM System](https://tdx.umsystem.edu/TDClient/66/MOOnline/KB/ArticleDet?ID=2193)). OAuth2 is no realistic way around this, since developer keys on Instructure-hosted Canvas "are issued by the admin of the institution" and the access tokens they produce last one hour and must be refreshed ([oauth.md](https://raw.githubusercontent.com/instructure/canvas-lms/master/doc/api/oauth.md)).

Policy shapes the architecture as much as the API does. Instructure's OAuth guide calls a manually generated token the simplest option "for testing", warns that "asking any other user to manually generate a token and enter it into your application is a violation of Canvas' API Policy", and requires OAuth for "applications in use by multiple users" ([oauth.md](https://raw.githubusercontent.com/instructure/canvas-lms/master/doc/api/oauth.md)). Instructure's Acceptable Use Policy also forbids sharing tokens with third parties and accessing the service through anything other than publicly supported interfaces, naming scraping as the example ([Instructure Acceptable Use](https://www.instructure.com/policies/acceptable-use)). A student running their own copy with their own token is therefore the most defensible design. No Instructure text explicitly approves student personal scripts, however, so the README must tell users to check their school's policy. The same rule settles what the public repository is: software each student hosts for themselves, never a shared instance that collects other students' tokens. Token expiry must be routine rather than an outage: the bot should read the token's `expires_at`, warn at 14, 7, 3 and 1 days before it — the schedule one existing Canvas sync tool already uses ([kaveengoswami-sketch/canvas-sync](https://github.com/kaveengoswami-sketch/canvas-sync)) — and treat a 401 carrying a `WWW-Authenticate` header as an expired or revoked token rather than a permissions error ([oauth.md](https://raw.githubusercontent.com/instructure/canvas-lms/master/doc/api/oauth.md)).

### Fallbacks trade accuracy for availability

When a school blocks tokens, the remaining options get steadily worse in a clear order.

| Mode | Needs | Gives | Lacks | Risk |
|---|---|---|---|---|
| **A. Token + Planner REST (primary)** | Personal token | Per-student dates, submission status, mark-done, points and weights | Undated items (use the Assignments API) | Lowest; tolerated for self-use |
| **B. Calendar feed (iCal)** | Feed URL from the Canvas Calendar page | Dated assignments with per-student overrides, 30 days back to 366 ahead | Submission status, undated items, ungraded to-dos, planner notes | Low; official feature, but the URL works like a password |
| **C. Browser session cookie** | A logged-in browser | The same JSON as mode A | Unattended login (SSO and multi-factor sessions expire) | Policy grey area; arguably works around a token ban |
| **D. Parsing Canvas notification emails** | Canvas emails set to "immediately" | New assignments, due-date changes, grades | Any "due soon" or "submitted" signal | Low, but sparse |
| **E. Screenshots + OCR or a vision model** | Manual screenshots | Whatever is visible | Stable IDs, the full list (the sidebar loads 14 items at a time), reliable dates | Highest; scraping-adjacent, sends data to a model |

The calendar feed is the right fallback. For a signed-in user's feed, Canvas covers **30 days back to 366 days ahead, applies per-student override dates and caps the feed at 1,000 items** ([calendar_events_api_controller.rb](https://raw.githubusercontent.com/instructure/canvas-lms/master/app/controllers/calendar_events_api_controller.rb)), and each event carries a stable `UID` of the form `event-assignment-<id>` and a `SUMMARY` that includes the course code ([calendar_event.rb](https://raw.githubusercontent.com/instructure/canvas-lms/master/app/models/calendar_event.rb)). The feed carries no submission state — the source shows an assignment query with overrides and no submission filter, and one open-source feed tool confirms the absence ([aaroncchung/ICS-Canvas-Notion-Sync](https://github.com/aaroncchung/ICS-Canvas-Notion-Sync)) — even though another tool claims submitted assignments "disappear" from the feed and relies on that to mark tasks complete ([DEVLlN/canvas-todoist-sync](https://github.com/DEVLlN/canvas-todoist-sync)), a claim that is unverified and should be tested rather than trusted. The bot should download the `.ics` itself rather than go through Google Calendar, which takes up to about 24 hours to refresh a subscription ([MIT Sloan EdTech](https://mitsloanedtech.mit.edu/support/how-to-sync-your-canvas-calendar-feed-to-outlook-in-office-365)), compare each download with the last by `UID` to catch new assignments and date changes, and rely on a manual Done button keyed by `UID` as the only way to stop reminders. The feed URL should be stored like a password, because no documented way to reset it was found.

Session-cookie reuse returns the same data as mode A, and community tools already depend on it: Canvas MCP servers use the browser session "so an admin policy blocking token generation cannot stop it" ([glama.ai listing](https://glama.ai/mcp/servers/kl1lsam9ig)), and a Canvas command-line tool directs users at token-blocking schools to session-cookie login ([thedavidweng/canvas-cli #16](https://github.com/thedavidweng/canvas-cli/issues/16)). But single sign-on and Duo sessions expire on schedules the school sets, and using cookies to get around a token ban is arguably circumventing an institutional control, so this mode belongs behind an off-by-default "experimental" flag with advice to ask IT first. Notification emails add little, because Canvas's "Due Date" notification fires when a due date *changes* rather than before a deadline ([Yale Canvas help](https://help.canvas.yale.edu/a/914669-how-do-i-modify-the-default-notification-settings)), so they can enrich data but never drive reminders. Screenshots are at most a later "paste a screenshot" helper, since sending them to a hosted vision model hands course data to a third party even though Instructure's API Policy says user information "should be considered and treated private" ([Instructure Canvas API Policy](https://www.instructure.com/policies/canvas-api-policy)).

## Telegram is the only free channel with buttons that works behind NAT

A Telegram bot meets every requirement at once. The Bot API has **no per-message fee** ([Unipile](https://www.unipile.com/is-the-telegram-api-free/)), and setup takes about five minutes: the student messages @BotFather to create the bot and receive its token, opens the new bot and presses Start (required, because a bot cannot open a conversation itself) ([advancedweb.hu](https://advancedweb.hu/the-easiest-way-to-set-up-a-chat-with-your-telegram-bot/)), and reads their chat ID from the bot's `getUpdates` response ([docs.quotesnap.net](https://docs.quotesnap.net/notification/how-to-get-telegram-bot-chat-id)). Long polling with `getUpdates` is an outbound request, so the bot works from a home network, a dorm or a Pi behind NAT; webhooks, by contrast, need a public HTTPS endpoint on port 443, 80, 88 or 8443, and the two methods cannot run at the same time ([aiogram setWebhook source](https://docs.aiogram.dev/en/latest/_modules/aiogram/methods/set_webhook.html)). Inline keyboard buttons return a callback carrying **1–64 bytes of `callback_data`** ([grammY types](https://deno.land/x/grammy_types@v3.6.2/markup.ts?source=)), plenty for `done:<id>` or `snz:<id>:2h`, and the bot must answer every callback or the button keeps spinning ([R telegram.bot docs](https://www.quantargo.com/help/r/latest/packages/telegram.bot/2.4.0/InlineKeyboardButton.html)). The per-chat limit of about one message per second ([grammY flood limits](https://grammy.dev/advanced/flood)) is irrelevant for one student.

Two implementation traps are well documented. MarkdownV2 rejects unescaped characters such as `- . ( ) ! +` with a 400 error — real bots have broken this way ([ScriptureBot PR #139](https://github.com/julwrites/ScriptureBot/pull/139)), and Canvas course names are full of those characters — whereas HTML mode only requires escaping `<`, `>` and `&` ([Telegram ParseMode mirror](https://tgrm.oss.hagever.com/types/Telegram.ParseMode.html)). And because anyone can find a bot by username and press /start, every update must be checked against the owner's ID before any other handler runs; python-telegram-bot's documented pattern is a `TypeHandler` in group −1 that raises `ApplicationHandlerStop` for everyone else ([PTB wiki](https://github.com/python-telegram-bot/python-telegram-bot/wiki/Frequently-requested-design-patterns)). On libraries, python-telegram-bot 22.8 (June 2026) and aiogram 3.31 (August 2026, Bot API 10.3) are both maintained ([PTB releases](https://github.com/python-telegram-bot/python-telegram-bot/releases); [aiogram releases](https://github.com/aiogram/aiogram/releases)), while the TypeScript library Telegraf has not released since February 2024 ([Telegraf releases](https://github.com/telegraf/telegraf/releases)). If the bot token leaks, `/revoke` in @BotFather disables it immediately ([GitGuardian](https://gitguardian.com/remediation/telegram-bot-token)).

Email is the right backup channel and a poor channel for repeated reminders. Sending from the student's own Gmail over SMTP needs only a 16-character **App Password, which requires 2-Step Verification**, no domain or DNS setup, and allows about 500 messages a day ([cli.nylas.com](https://cli.nylas.com/guides/gmail-smtp-settings)); Google calls App Passwords "unnecessary in most cases" but has published no end date for them ([cli.nylas.com](https://cli.nylas.com/guides/gmail-smtp-settings)). Transactional providers all require a domain the student controls with SPF and DKIM records: Resend's free plan allows 3,000 emails a month capped at 100 a day ([Resend](https://resend.com/blog/new-free-tier)), and SendGrid **ended its free plan on May 27, 2025** ([SendGrid on Wikipedia](https://en.wikipedia.org/wiki/SendGrid)). Email has no native buttons, so a "mark done" link would need a public web endpoint and would give up the advantage long polling provides. Instructure's own product blog also reported that 50% of students "don't always read emails from academic departments" ([Instructure product blog](https://community.canvaslms.com/t5/The-Product-Blog/Streamlining-Canvas-Push-Notifications/bc-p/426145)). Email should therefore carry a copy of the daily digest and serve as the alert path when Telegram fails, not carry the two-hour reminders, and because an App Password signs in to the whole mailbox, a separate sending account limits the damage of a leak.

SMS is where the student's "I have no phone number for a bot" question has a definite answer. A bot cannot text from nowhere: it rents a number from a messaging-API company such as Twilio, Telnyx or Plivo and calls that company's API, and in the US **carriers have blocked unregistered application-to-person traffic on ordinary "10DLC" numbers since February 2025** ([Telnyx 10DLC FAQ](https://support.telnyx.com/en/articles/3679260-frequently-asked-questions-about-10dlc)). An individual can register on Twilio as a Sole Proprietor for a one-time brand fee of about $4.50 and $15 campaign vetting, plus about $2 a month per campaign, limited to one campaign, one number and 1,000 messages a day ([Twilio support](https://support.twilio.com/hc/en-us/articles/1260803965530)). On top of that come roughly $0.008 per message plus carrier pass-through fees, about $1.15 a month for the number, and 1–3 weeks of registration lead time ([textbee.dev](https://textbee.dev/blog/twilio-pricing-real-cost-breakdown); [sociocs](https://www.sociocs.com/post/twilio-10dlc-explained/)). Toll-free numbers are no easier: since **February 17, 2026** Twilio requires a business registration number on new toll-free verification requests (sole proprietors excepted), and since **September 15, 2026** it also requires privacy-policy and terms URLs ([Twilio changelog](https://www.twilio.com/en-us/changelog/business-registration-numbers-required-for-toll-free-messaging-p); [Twilio changelog](https://www.twilio.com/en-us/changelog/toll-free-verification-now-requires-privacy-policy-and-terms-and)). The old free trick of emailing `number@carrier-gateway` is dead: AT&T shut its gateway on June 17, 2025 ([Princeton SCAD IT](https://scad.princeton.edu/news/att-discontinues-email-text-and-text-email-service)), T-Mobile's stopped in late 2024 ([sigspan](https://sigspan.com/carrier-gateway-shutdown)), and Verizon's is unreliable and scheduled to close on March 31, 2027 ([sigspan Verizon](https://sigspan.com/verizon-email-to-text-gateway)). Rules outside the US differ — India, for example, requires registration on TRAI's DLT system with pre-approved message templates ([AWS India sender ID](https://docs.aws.amazon.com/sms-voice/latest/userguide/registrations-sms-senderid-india.md)). Adding those figures up, US SMS would cost about **$7–8 a month plus about $19.50 up front**, plus paperwork, for a channel with no buttons and only keyword replies. It is not worth it.

Dedicated push apps are the alternative for students who won't use Telegram. **ntfy** is free and open source; publishing is a plain HTTP POST with five priority levels and up to three action buttons ([ntfy publish docs](https://github.com/binwiederhier/ntfy/blob/main/docs/publish.md)), and it is actively maintained (v2.31.0, October 15, 2026) ([ntfy releases](https://github.com/binwiederhier/ntfy/releases)). On the public ntfy.sh server, though, "your topic name functions as a password" ([ntfy Terms](https://docs.ntfy.sh/terms/)), a self-hosted server must forward through `upstream-base-url: https://ntfy.sh` or iOS delivery "can take hours" ([ntfy config docs](https://github.com/binwiederhier/ntfy/blob/main/docs/config.md)), and its `http` action buttons are sent from the phone, so the URL they call must be reachable from the phone's network — a problem Telegram callbacks don't have. **Pushover** costs **$4.99 once per platform** and includes 10,000 messages a month ([Pushover pricing](https://pushover.net/pricing); [Pushover limits](https://support.pushover.net/i12-message-size-and-frequency-limitations)), and it is the only service that repeats an alert until acknowledged: emergency priority re-alerts every 30 seconds or more for at most three hours, with acknowledgement receipts ([Pushover receipts API](https://pushover.net/api/receipts)). That makes it an optional last-hours escalation rather than a replacement for the two-hour schedule. The remaining options are weaker. Gotify has no first-party iOS app ([selfhostyourself](https://www.selfhostyourself.com/services/gotify)); Discord webhooks cannot send direct messages, so a full bot application is needed ([cybrancee](https://cybrancee.com/blog/discord-webhooks-explained-what-they-can-and-cant-do/)); WhatsApp has billed per template message since July 1, 2025 and requires Meta business onboarding ([YCloud](https://www.ycloud.com/blog/whatsapp-api-pricing-update)); and Signal via the unofficial signal-cli client triggers "proof required" CAPTCHA lockouts that must be solved by hand ([Healthchecks.io blog](https://blog.healthchecks.io/hp-rewrite/4729aced94ebc929baf36eba9b9eca5c)).

| Channel | Cost here | Two-way buttons | Works behind NAT without a public URL | Verdict |
|---|---|---|---|---|
| Telegram bot | Free | Yes (callbacks) | Yes (long polling) | **Primary** |
| Gmail SMTP + App Password | Free | Links only | Sending yes; links no | **Digest copy and fallback alerts** |
| ntfy | Free (ntfy.sh) or self-hosted | Up to 3 actions | Sending yes; actions need a reachable URL | Option for users without Telegram |
| Pushover | $4.99 one-time per platform | Acknowledgement on emergency priority | Yes (poll the receipt) | Optional escalation |
| Discord bot | Free | Yes | Yes | Only if the student already lives in Discord |
| SMS (Twilio 10DLC) | About $7–8/month + $19.50 one-time | Keyword replies | Inbound needs a webhook | **Skip** |
| Email-to-SMS gateway | Free | No | — | **Dead** |

In the code, delivery should sit behind a `Notifier` interface with Telegram, SMTP and in-memory fake implementations. Apprise (BSD-2-Clause, v2.0.1) can fan one-way messages out to more than 100 services from URLs such as `tgram://` and `ntfys://`, but it cannot receive button presses ([caronc/apprise](https://github.com/caronc/apprise)), which makes it a good optional "extra channels" add-on and a poor primary Telegram integration.

## One idempotent tick loop beats a scheduler full of jobs

Scheduling one job per reminder makes the job store a second source of truth, turning every due-date edit, submission and restart into a reconciliation problem, and the leading Python scheduler shows why that is risky. APScheduler 3.x needed repeated DST fixes through 2025–2026 — **3.11.2 fixed a cron job scheduled during a DST transition sending the scheduler into an infinite loop**, and an unreleased fix addresses `AsyncIOScheduler` "permanently stopping the processing of jobs" after an exception ([APScheduler 3.x version history](https://github.com/agronholm/apscheduler/blob/3.x/docs/versionhistory.rst)) — while the 4.0 line is still alpha (4.0.0a6, April 2025) and warns "do NOT use this release in production" ([PyPI APScheduler](https://pypi.org/project/APScheduler/); [APScheduler master history](https://github.com/agronholm/apscheduler/blob/master/docs/versionhistory.rst)). The sturdier design is one process with two loops: a **sync loop** every 10–15 minutes that upserts Canvas items into SQLite, and a **notify loop** every 60 seconds that works out what is owed from stored state and records every send under a deterministic key protected by a UNIQUE constraint. Because each tick recomputes everything from stored state, the loop is restart-safe and idempotent by construction, and the same `tick()` function can later be triggered by systemd, Cloudflare cron or EventBridge without a separate codebase.

The 8 AM digest needs no cron arithmetic. On each tick the bot computes `today_local = now_utc.astimezone(tz).date()` and that day's 08:00 in the student's IANA time zone, and sends if the current time is past it and no row exists for the key `digest:{user}:{local_date}`. Keying on the local date handles DST, restarts and late ticks in one step, and **8:00 AM never falls inside a DST gap or overlap**, because clocks change around 00:00–03:00. Python's `zoneinfo` resolves ambiguous times correctly through PEP 495 `fold`, and its docs recommend depending on the `tzdata` package because slim containers and Windows lack a system time-zone database ([Python zoneinfo docs](https://docs.python.org/3/library/zoneinfo.html)). The digest should have a grace window (for example until 12:00, after which a missed digest is skipped rather than sent late), sync immediately before sending, and **never say "nothing due" when the real cause is a failed sync** — a stale digest must say "last synced HH:MM".

The two-hour reminders are where DST and duplicate messages cause real bugs, so everything there runs on UTC durations, never wall-clock slots. The recommended model is **one combined reminder cycle per user**. An item is urgent when it is not done and `0 < due_at_utc − now_utc ≤ 24h`. When the first urgent item appears, the cycle is anchored at that moment in UTC; slot *n* fires at anchor + 2h·*n* and sends **one message listing every currently urgent item** under the key `rem:{user}:{anchor}:{n}`; and the cycle ends when nothing urgent remains. An item that becomes urgent mid-cycle joins the next slot, at most two hours away, unless it has less than two hours left (a last-minute posting), which triggers an immediate alert. Before each slot the bot syncs again or confirms a sync within the last few minutes, so "you still haven't submitted" never goes out right after a submission, and storing `due_at` with each item means an extension resets that item cleanly. Sending is at-least-once — insert the key as `pending`, send, mark it `sent`, and retry stale `pending` rows on restart — which means a crash between sending and marking produces at most one duplicate, the trade-off a transactional outbox makes ([microservices.io](https://microservices.io/patterns/data/transactional-outbox.html)). Downtime collapses naturally into catch-up, because after an outage only the current slot fires; that fixes the failure one archived Discord bot admits to, where a reminder due while the bot was offline "will NOT be sent at all" ([jnarezo/canvas-discord-bot](https://github.com/jnarezo/canvas-discord-bot)).

Quiet hours and overdue handling are the two places where the literal spec, "every 2 hours until submitted", should become configurable defaults. Canvas deadlines cluster at 23:59 — Canvas even treats 23:59 due times as all-day ([abstract_assignment.rb](https://raw.githubusercontent.com/instructure/canvas-lms/master/app/models/abstract_assignment.rb)) — so a 22:00 quiet-hours start would silence exactly the two hours that matter most. The recommended default is **quiet hours from 00:00 to 08:00**, preceded by a "due overnight" warning for anything due inside them. For a typical 23:59 deadline that yields roughly eight reminders plus the digest instead of twelve, with the digest itself serving as the first reminder after quiet hours. At the deadline the two-hour cadence stops, the bot sends a single "now overdue" message, and the item stays in the digest's overdue section until `lock_at` or for seven days; continuing two-hour reminders after the deadline while late work is still accepted should be an opt-in setting.

Storage should be **SQLite in WAL mode on a local volume**, where "readers do not block writers and a writer does not block readers" and which must not sit on a network filesystem ([SQLite WAL](https://www.sqlite.org/wal.html)). Items are keyed by stable Canvas IDs rather than titles, because titles change and title keys create duplicates, and backups use `sqlite3 .backup`. Hosted Postgres (Neon, Supabase) or Cloudflare D1 only makes sense for a serverless or multi-user phase, and D1's free-tier limits became hard limits on September 1, 2026 ([Cloudflare changelog](https://developers.cloudflare.com/changelog/post/2026-09-01-d1-free-tier-limit-enforcement/)). A minimal schema needs five tables:

| Table | Columns |
|---|---|
| `items` | `plannable_type`, `plannable_id`, `course`, `title`, `due_at_utc`, `lock_at_utc`, `html_url`, `points`, `group_weight`, `submission_types`, `done_source`, `user_done_at`, `snoozed_until`, `last_synced_at` |
| `courses` | `id`, `name`, `hidden` |
| `notifications` | `key` (UNIQUE), `kind`, `status`, `sent_at`, `error` |
| `settings` | `tz`, `digest_hour`, `quiet_start`, `quiet_end` |
| `kv` | `last_successful_sync_at`, `token_expires_at`, `token_status`, `schema_version` |

The recommended stack is **Python 3.12 or 3.13** with python-telegram-bot 22.x, chosen for its documented owner-gate pattern and single-bot `run_polling` (aiogram 3.x is equally valid); a small custom `httpx` Canvas client in place of `canvasapi`, which lacks the planner call and pulls in `pytz`, `arrow` and synchronous `requests` ([PyPI canvasapi](https://pypi.org/project/canvasapi/)); pydantic-settings for configuration that fails fast on bad values; and `zoneinfo` with `tzdata`. TypeScript, with grammY, croner and native Temporal in Node 26, wins only if Cloudflare Workers is the main deployment target ([Help Net Security](https://www.helpnetsecurity.com/2026/05/07/node-js-26-released/); [croner](https://github.com/Hexagon/croner)).

GitHub Actions deserves a specific warning because so many student projects lean on it. GitHub's own docs say scheduled runs "can be delayed during periods of high loads" and that "some queued jobs may be dropped" ([GitHub Docs](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows)); a July 2026 report described a daily job on a new free account running **8–14 hours late** and being skipped entirely on at least two days ([GitHub Community #201738](https://github.com/orgs/community/discussions/201738)); and in public repositories, scheduled workflows are disabled automatically after 60 days without activity ([GitHub Docs](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows)). The 2026 `timezone:` field fixes DST, not punctuality. A laptop that sleeps is a hidden version of the same problem: the grace window rescues a late digest but not the reminders.

Packaging should make the always-on path easy. The release workflow publishes one multi-architecture (amd64 and arm64) image to GitHub Container Registry, using GitHub's native arm64 runners so no emulation is needed ([GitHub-hosted runners](https://docs.github.com/en/actions/reference/runners/github-hosted-runners)) and `GITHUB_TOKEN` so the package links to the repository ([GitHub Container registry docs](https://docs.github.com/en/packages/working-with-a-github-packages-registry/working-with-the-container-registry)). The shipped `docker-compose.yml` should include a named volume for the database, `restart: unless-stopped`, a `HEALTHCHECK` that reads `last_tick_at` from the database rather than calling Canvas, and rotated JSON logs so a Pi's SD card doesn't fill. Monitoring comes from healthchecks.io acting as a dead man's switch — it "raises an alert as soon as a ping does not arrive on time" ([healthchecks.io docs](https://healthchecks.io/docs/)) and its free tier allows 20 checks ([healthchecks.io pricing](https://healthchecks.io/pricing/)). The bot pings after each successful sync and sends `/fail` when Canvas rejects the token, which catches what the bot cannot report itself: a dead host, a stopped Docker daemon or a silently stalled scheduler. Errors are handled as follows.

| Error | Response |
|---|---|
| Canvas 429 or 403 throttling, 5xx errors, timeouts | Retry with capped exponential backoff and **full jitter**, `sleep = random(0, min(cap, base·2^attempt))` ([AWS Architecture Blog](https://aws.amazon.com/blogs/architecture/exponential-backoff-and-jitter/)) |
| Canvas 401 with a `WWW-Authenticate` header | Stop calling Canvas and send one Telegram alert with renewal steps |
| Many consecutive failed syncs | Open a circuit breaker; keep reminding from the last known state, marked as stale |
| Telegram 429 | Wait as long as `retry_after` says |

## Treat the Canvas token as a password that skips MFA

The Canvas token is by far the most valuable secret in the system. Universities warn that tokens bypass single sign-on and multi-factor authentication and that "the downstream impact of a compromised token can exceed that of a stolen password" ([University of Missouri System](https://tdx.umsystem.edu/TDClient/66/MOOnline/KB/Article/2193/Canvas-user-API-token-policy)). Because student tokens normally inherit full permissions ([tokens_controller.rb](https://raw.githubusercontent.com/instructure/canvas-lms/master/app/controllers/tokens_controller.rb)), a leaked token could submit or replace assignments (an academic-integrity incident blamed on the student), message instructors as the student, read grades and download course files. And because a token can create further tokens for its own user, the README's leak runbook must say to delete *every* unknown token, not just the leaked one. The other secrets matter less but still need care: the Telegram bot token gives full control of the bot and its message history ([GitGuardian](https://gitguardian.com/remediation/telegram-bot-token)), a Gmail App Password opens the whole mailbox, and a topic on the public ntfy.sh server works like a shared password ([ntfy FAQ](https://docs.ntfy.sh/faq/)).

The controls follow from that threat model. Canvas cannot scope a student token, so the code has to enforce **read-only access itself**: the client allows only GET requests plus one opt-in write — a planner override (`POST /api/v1/planner/overrides` with `marked_complete:true`), so that tapping Done also checks the item off in Canvas ([planner_overrides_controller.rb](https://raw.githubusercontent.com/instructure/canvas-lms/master/app/controllers/planner_overrides_controller.rb)) — and SECURITY.md should state that submission and messaging endpoints will never be implemented. Every Telegram update from anyone other than the owner is dropped, and the bot opens no inbound ports because it uses long polling; if webhooks are ever added, they must check Telegram's `secret_token` header ([aiogram setWebhook docs](https://docs.aiogram.dev/en/latest/api/methods/set_webhook.html)). Secrets reach the process as files, through Compose secrets mounted at `/run/secrets` and read via `*_FILE` variables, or through a `.env` file with `chmod 600`, because plain environment variables appear in `docker inspect` ([Phase.dev](https://phase.dev/blog/docker-compose-secrets/); [StackHarbor](https://stackharbor.com/en/knowledge-base/docker-secrets-handling/)). OWASP lists access tokens among values that must never be logged ([OWASP Logging Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html)), and the subtle leak here is that **the Telegram token sits in the API URL path** (`/bot<TOKEN>/sendMessage`), so any INFO-level request log from the HTTP client exposes it. The fix is to hold secrets in `SecretStr`, set the `httpx` and `httpcore` loggers to WARNING, add a regex redaction filter, and add a test that runs the bot with placeholder secrets and asserts they never appear in captured logs.

Text from Canvas is untrusted input, and the Canvas host must be pinned. Every interpolated field is escaped for Telegram's HTML mode; assignment descriptions, which are HTML and can name classmates, are never forwarded; and an `html_url` is emitted only when its scheme is `https` and its host matches the configured Canvas host. The base URL is validated as HTTPS only, with no user info and no raw IP addresses, and the client never follows a redirect or a pagination `Link` to a different host while carrying the token, in line with OWASP's SSRF guidance to use allowlists and disable redirects ([OWASP SSRF cheat sheet](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html)). Privacy law mostly constrains a hosted version rather than a personal one. FERPA governs institutions, and at a college the student is the "eligible student" who holds the rights ([Caltech FERPA guide](https://finaid.caltech.edu/documents/29302/FERPA-Student.pdf)), so pulling one's own records into one's own bot is not an institutional disclosure — an inference, not a regulator's statement. For an EU student, GDPR's household exemption covers purely personal use and "must be read very restrictively" ([Irish DPC](https://dataprotection.ie/en/faqs/general/what-household-exemption); [Mondaq](https://www.mondaq.com/data-protection/1773198/one-man-controller-the-responsibility-of-individuals-under-the-gdpr)), so running the bot for classmates would end it. Even for one user, the bot should fetch only course names, titles, dates, submission flags, points and weights, keep grades, comments and descriptions out of messages sent through third parties such as Telegram and Gmail, and purge items a fixed number of days after their due date.

The public repository should switch on everything GitHub offers for free. Secret-scanning push protection is on by default for new public repositories owned by personal accounts ([GitHub changelog](https://github.blog/changelog/2024-03-11-secret-scanning-and-push-protection-are-enabled-by-default-on-new-public-repositories/)) and should be paired with gitleaks in pre-commit; private vulnerability reporting with a SECURITY.md ([GitHub Docs](https://docs.github.com/en/code-security/how-tos/report-and-fix-vulnerabilities/report-a-vulnerability/privately-reporting-a-security-vulnerability)), CodeQL default setup ([GitHub Docs](https://docs.github.com/en/code-security/how-tos/scan-code-for-vulnerabilities/configure-code-scanning/configuring-default-setup-for-code-scanning)) and Dependabot with grouped, cooled-down version updates complete the baseline. Workflow hardening matters because of a concrete incident: in March 2025 attackers repointed the tags of tj-actions/changed-files to a malicious commit that leaked CI secrets in about 23,000 repositories, and **workflows that pinned the action to a full commit SHA were unaffected** ([Safeguard](https://safeguard.sh/resources/blog/tj-actions-changed-files-github-actions-supply-chain-compromise)). Every action should therefore be pinned to a full SHA, every workflow should start with `permissions: {}` and grant permissions per job, `pull_request_target` should never be used, and zizmor should lint the workflows. Dependencies are locked in `uv.lock`, which hashes every distribution ([pydevtools](https://pydevtools.com/handbook/how-to/how-to-pin-dependencies-with-hashes-in-uv/)), and audited with `pip-audit` ([pip-audit](https://pypi.org/project/pip-audit/2.3.2)); images are published with artifact attestations, which meet SLSA Build Level 2 ([GitHub Docs](https://docs.github.com/actions/security-guides/using-artifact-attestations-to-establish-provenance-for-builds)), as immutable releases, generally available since October 28, 2025 ([GitHub changelog](https://github.blog/changelog/2025-10-28-immutable-releases-are-now-generally-available/)). The container runs as a non-root user with a read-only root filesystem, `cap_drop: [ALL]`, `no-new-privileges` and no published ports. Apache-2.0 is the recommended license because it adds an explicit patent grant to MIT-style permissiveness ([credativ](https://www.credativ.de/en/blog/credativ-inside/understanding-open-source-licenses-gpl-mit-apache-compared/)).

### Make the scheduler a pure function and attack it with time

Most real bugs in a reminder bot are time bugs, so the core should be a pure function, `plan(now, items, sent_log, settings) → messages_to_send`, with the clock passed in rather than read from `datetime.now()`. Integration tests should use **time-machine** rather than freezegun, since a 2026 re-benchmark confirmed that freezegun's setup cost grows with the number of loaded modules while time-machine's stays constant ([Adam Johnson](https://adamj.eu/tech/2026/08/03/python-time-machine-o1-freezegun-on/)); note that time-machine lets time keep moving unless `tick=False` is set ([time-machine docs](https://time-machine.readthedocs.io/en/latest/comparison.html)). Table-driven tests must cover the next real transitions — **the EU falls back on October 25, 2026 and the US on November 1, 2026, within weeks of today**, so the bot's first month in production will cross one — along with 23:59 deadlines, a null `due_at`, `lock_at` before `due_at`, section overrides, a due date extended after a reminder was sent, a restart mid-cycle, Canvas 401, 403, 429 and 5xx responses, and multi-page results. Hypothesis property tests then assert, over arbitrary items, time zones and poll sequences, that no key is ever sent twice, nothing is sent after the deadline or after the item is marked done, and every slot fires within one poll interval of its target. Hypothesis's datetime strategies understand `fold`, but their source warns the logic is wrong for zones with negative DST such as Europe/Dublin ([Hypothesis source](https://hypothesis.readthedocs.io/en/latest/_modules/hypothesis/strategies/_internal/datetime.html)), so that zone deserves its own example tests. Recorded Canvas responses come from VCR.py cassettes with `filter_headers` stripping `Authorization` ([VCR.py](https://vcrpy.readthedocs.io/en/latest/advanced.html)), and a CI step greps the cassettes for token patterns. A `FakeNotifier` receives adversarial titles — `<b>`, `&amp;`, `*_[]()`, emoji, 5,000 characters, embedded newlines — while ruff with the `DTZ` rules (which flag naive datetimes) and `S` rules, plus `mypy --strict`, guard the code statically. Mutation testing is worth reserving for the scheduler module alone.

## No existing tool reminds you until the work is submitted

Canvas itself leaves the gap open. Its "Due Date" notification covers due-date changes, and some schools default it to a weekly summary ([Indiana University KB](https://www.kb.indiana.edu/d/bfdl); [Yale](https://help.canvas.yale.edu/a/914669-how-do-i-modify-the-default-notification-settings)). A 2018 Canvas Idea asking for automatic reminders 24 hours before a deadline, sent to students who haven't submitted, is still open ([Canvas Idea](https://community.canvaslms.com/t5/Canvas-Ideas/Notifications-Automatic-due-date-reminder-notifications/idc-p/488024)). The only built-in pre-deadline reminder lives in the Canvas Student mobile app, where it is set by hand for each assignment on each device from presets of 5 minutes to 1 week, up to 10 per assignment ([Canvas Guide](https://canvas.screenstepslive.com/m/18555/l/1786419-how-do-i-create-a-reminder-for-an-assignment-or-quiz-in-the-canvas-student-app-on-my-android-device)). The web To Do list also has an open known issue in which students with more than 50 completed items in two weeks see "Nothing for now" ([Canvas Known Issues](https://community.canvaslms.com/t5/Known-Issues/OPEN-Students-with-more-than-50-completed-items-in-the-past-two/m-p/656708)). Better Canvas reaches about a million Chrome users ([Chrome Web Store](https://chrome.google.com/webstore/detail/better-canvas/cndibmoanboadcifjkjbdpjgfedanolh?hl=en)), but extensions only work while the browser is open on Canvas, and the open feature requests on Tasks for Canvas — task priority, reminders, a two-week look-ahead, hiding courses — read like this bot's scope ([Tasks for Canvas issues](https://github.com/jtcheng26/canvas-task-extension/issues?q=is%3Aissue)).

### A transparent 100-point score ranks the digest

The research favors batched, explainable prompts over constant pings. In Fitz et al. (2019, 237 participants), batching notifications three times a day improved attention, mood and sense of control, while hourly batching barely differed from control ([Duke Scholars](https://scholars.duke.edu/publication/1402953)). A systematic review of SMS medication reminders found that reminders sent once a day or more had smaller effects than less frequent ones, and patients rated high frequency poorly ([PMC4939231](https://pmc.ncbi.nlm.nih.gov/articles/PMC4939231/)). Coursework evidence is mixed: a randomized Norwegian study found text nudges had no effect on problem-set submission ([NTNU](https://www.ntnu.no/ojs/index.php/nikt/article/view/5714)), and in Patterson's MOOC experiment a passive reminder tool did no better than control while a **self-set commitment device raised course completion by 40%** ([Cornell eCommons](https://ecommons.cornell.edu/entities/publication/0ccc8fbd-c323-4536-b4a3-dd587b4f643c)). Repetition still works close to a deadline — weekly gym reminders produced an "immediate and recurrent" response to every single reminder ([DIW](https://www.diw.de/de/diw_01.c.533841.de/publikationen/externe_referierte_aufsaetze/2017_0009/effective_reminders.html)) — and if-then "when will I start" plans showed d = 0.65 across 94 tests ([Gollwitzer & Sheeran](https://kops.uni-konstanz.de/signposting/describedby/cf394f1f-49d8-4256-bf24-df7af124514a)). mHealth research, meanwhile, finds habituation when repeated notifications look alike ([CHI 2024](https://dl.acm.org/doi/full/10.1145/3613904.3641993)). Taken together, the 8 AM digest is the main tool, the two-hour reminders should be a final-day escalation that is consolidated into one message, varied in wording and governed by quiet hours and one-tap snooze, and a "when will you start?" prompt on HIGH items is a strong phase-2 feature.

For ranking, a simple additive score combines urgency, importance and effort, borrowing from Temporal Motivation Theory's value-over-delay ([Steel 2007](https://prism.ucalgary.ca/handle/1880/47914)) and WSJF's cost-of-delay-over-size ([ProductPlan](https://www.productplan.com/glossary/weighted-shortest-job-first)) while staying explainable on every line of the digest. It deliberately does not divide by effort, because pure WSJF would push trivial tasks above heavily weighted ones.

| Component | Points | Rule |
|---|---|---|
| Urgency U | 0–50 | Overdue but still accepting submissions: 50 · ≤24 h: 45 · ≤48 h: 35 · ≤72 h: 25 · ≤7 days: 12 · >7 days: 4 |
| Importance I | 0–35 | Share of final grade ≥15%: 35 · ≥8%: 28 · ≥4%: 20 · ≥1.5%: 12 · >0: 6 · ungraded or 0 points: 2. Add +5 for exam, midterm, final or project keywords (cap 35) |
| Effort pressure E | 0–15 | Slack = hours left − 1.5 × estimated effort. Slack ≤0: 15 · ≤24 h: 10 · ≤72 h: 5 · otherwise 0 |

Share of final grade is `group_weight × points_possible / Σ points in that group` (excluding items marked `omit_from_final_grade`) in courses with weighted assignment groups, and `points_possible / Σ course points` elsewhere; when it cannot be determined, the digest says "weight unknown". Default effort estimates, which the student can override, are 1 hour for a discussion, quiz or reading, 2 for homework, 3 for a lab, 6 for an essay or project and 8 for exam prep. Items fall into four tiers. **URGENT** covers anything not done and due within 24 hours, or overdue but still accepting submissions, and by default only its pre-deadline items receive two-hour reminders. **HIGH** covers a score of 55 or more, or anything due within 72 hours and worth at least 8%, or due within 7 days and worth at least 10%, or with slack under 24 hours. **MEDIUM** covers scores of 30–54 and **LOW** everything below 30. Within a tier, items sort by due time and then by score, and each line explains itself — for example "URGENT · due in 5 h 20 m (Tue 11:59 PM) · ≈12% of grade · quiz · est. 1 h", with "start by Mon 6 PM" added for HIGH items. The digest opens with tier counts, then lists URGENT, HIGH, a collapsed MEDIUM and LOW block, an Overdue/Missing section and a short "Done yesterday" line, with every item linked back to Canvas. These thresholds are design choices drawn from prior art rather than validated findings, since no published evaluation of such a score exists, so the PRD should make them configurable and tune them on real use.

A one-week technical spike should settle the open questions before the PRD is frozen. It needs to establish whether submitted assignments really disappear from the calendar feed, when a New Quiz sets `submitted_at`, whether `GET /api/v1/users/self` exposes a profile `time_zone` the bot could use as its default, what exact JSON the REST `/courses/:id/assignment_groups` endpoint returns, whether Instructure's hosted Canvas enables the `planner_submittable_completion_filter` flag, whether ntfy action buttons work from the iOS lock screen, and how Telegram's `disable_notification` and 4,096-character message limit behave, since none of these could be checked against official documentation. Above all, the student should confirm their own school's token policy before writing code, because that single fact decides whether mode A or mode B is the product.

## Conclusion

The difficult engineering here is trust, not messaging. A reminder bot fails the moment it nags about work already submitted or reports "nothing due" when the sync actually broke, because after either failure the student starts ignoring it — and the habituation research shows how quickly that happens. Submission-detection latency, stale-data handling and restart-safe deduplication are therefore the real product, and ETag-polled Planner data, a stored-state tick loop and an external heartbeat are what deliver them; the channel, the host and the scoring weights can all change without touching that core.

Two strategic implications follow. The access landscape is moving against student tokens, with more school bans and a 120-day cap now in Canvas core, so a project that treats the calendar feed with manual Done as a first-class mode rather than an afterthought will keep working at exactly the schools where token-only tools stop. And the evidence suggests the two-hour nag is the weakest part of the original spec while the digest and self-set commitments are the strongest, which the bot can test on its own user by logging how many hours before each deadline work is actually submitted and whether reminders or start-time prompts moved that number — a feedback loop for tuning cadence and score that no existing tool has.
